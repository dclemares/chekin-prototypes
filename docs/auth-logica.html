Chekin · Sign-in prototype

How the authentication flow works

Seven screens that behave like a graph, not a sequence. The whole block hangs off a single decision — what the email address turns out to be — and off one rule repeated everywhere: never confirm that an account exists until someone has proved it is theirs.

The decision everything hangs off

The address is typed once. What happens next is not the user's choice — it is determined by the state that address is in. There are three, and they are mutually exclusive.

No account

Does not exist

Nobody has registered it. The way forward is creating the account, not retrying the sign-in.

Has account

Exists, with a password

Created by email. The password is the only key; the provider does not open it.

Google only

Exists, no password

Created with Google. There is no password to ask for, so asking for one would be a lie.

One door, three ways out

Email and Google are two ways of identifying the same person, so they branch on the same value. They did not before: the Google button went to the dashboard whatever the address turned out to be, which left two of the three states unreachable through it.

The recovery chain

Four screens linked by an email that leaves the app and comes back. The user abandons the browser halfway through, and that interruption explains almost every decision on these screens.

Screen by screen

Each block covers what the screen does, what it branches on and where it leads. The identifier is the real URL fragment.

#login

The way in

One door for signing in and for signing up. Takes the email and decides.

Branches into

no account
Jumps to #r-account with the address carried across. It is never typed twice.
has a password
Reveals the password field in place, with no navigation, so password managers keep up.
Google only
Goes to #sso-only. It does not ask for a password that does not exist.

Once the password shows

  • The Google button and its divider stand down: that account is not opened by the provider, so offering it leads down the wrong path.
  • The terms line goes too. Someone who already has an account is not accepting terms again by typing their password.
  • The address stays as a chip with a Change action, correctable without starting over.

Account enumeration: this is the point where the system reveals whether an address is registered. It is the trade-off the pattern carries, and worth settling with whoever owns security before production.

#sso-only

Account with no password

The address exists but was created with Google. Says why there is no password to ask for.

Why it exists

  • Registration offers Google, so these accounts exist. Without this screen the only possible answer was a wrong-password error about a password that was never set.
  • Names the address it is talking about, with a Change action.

Leads to

Dashboard continue with Google #recovery lost access to that account #login back
#twofactor

Verification code

Second factor after a correct password. Six digits, sent by email.

Behaviour

auto-submit
The sixth digit sends it. Reaching for a button after typing the code is a step nobody needs.
one-time-code
Declared on the first box, so phones offer the code they just received without switching apps.
paste
Pasting six digits into any box distributes them across all of them.
navigation
Arrows move between boxes and backspace clears as it steps back. Fixing the third digit does not mean deleting the rest.
wrong code
Clears the boxes and returns focus to the first.
expiry
10 minutes, said on screen. It is the reason a correct code stops working.

Leads to

Dashboard valid code #login back
#recovery

Request a link

Takes the address the reset link should go to.

Behaviour

  • The same answer every time. Whatever is typed, it goes to #check-email. Whether an account exists is not something a recovery form should confirm to whoever filled it in.
  • Arrives with the address already filled when you come from login — you typed it one screen ago.
  • It is a real form: Enter submits.

Leads to

#check-email always #login back
#check-email

Email sent

A waiting screen. Its job is to get the user out of here and into their inbox.

Behaviour

primary action
Opens the inbox. Where the domain gives the provider away it names and links it — Gmail, Outlook, Yahoo, iCloud, Proton; for work domains it does not guess and hands off to the OS.
resend
On a 30s cooldown. Without one the button invites hammering, and every press is another email.
order
The spam hint sits before the resend: it is the cheaper thing to try first.
expiry
30 minutes, said here rather than discovered on the way back.

Leads to

#reset from the link in the email #login back
#reset

New password

Reached from the email, often on another device. Sets the new password.

Behaviour

four rules
8+ characters, uppercase, number and symbol, on one row of slots that tick independently. What is shown is what is enforced.
empty confirm
Says "repeat the password", not "they don't match". With no second password there is nothing to disagree.
names the account
You arrive from a link: knowing which account you are changing is not a detail.
consequence
Warns that it signs you out everywhere else, before it does it.

Leads to

#reset-success valid password #login back
#reset-success

Confirmation

Closes the chain and, without calling itself one, is the flow's only security alert.

Behaviour

  • Names which account changed and confirms that every other session was signed out.
  • Offers to start over if it wasn't you. A reset you did not ask for is how you find out someone else has your inbox, and this is the only screen that can tell you.
  • Returns to login with the address filled in.

Leads to

#login sign in with the new one #recovery that wasn't you

What repeats across all seven

Four decisions that belong to no single screen and explain why the set behaves the same way throughout.

01

No dead buttons

Nothing sits greyed out waiting. Validation happens on submit and points at the field that failed, because a disabled button never says which one it is.

02

Every screen names itself

Any screen that talks about an account says which. People arrive from emails and from other devices, and context does not travel on its own.

03

The exit sits outside

The card holds what helps you finish. "Back to login" goes below it: that is abandoning the task, not part of it.

04

Scaffolding stays out

Demo notes and shortcuts live in the prototype's own bar, not inside the cards where they read as product.
